## 1. Resource Sharing (The Battleground)

**The Concept:**
In Java, threads are like workers. To do their jobs, they need memory. Java memory is split into two parts:
1.  **The Stack (Private):** Each worker gets their own private workspace.
2.  **The Heap (Shared):** A massive public warehouse where all Objects live.

**Resource Sharing** happens when two or more workers (Threads) go into the Heap and try to touch the exact same Object (like a Bank Account) at the exact same time.

### 📊 VISUAL: The Memory Map
```text
=========================================================
                 JAVA VIRTUAL MACHINE (JVM)
=========================================================

  [THREAD 1's PRIVATE STACK]        [THREAD 2's PRIVATE STACK]
  +------------------------+        +------------------------+
  | Local Var: amount = 50 |        | Local Var: amount = 50 |
  +------------------------+        +------------------------+
              \                          /
               \ (Both reach out to...) /
                \                      /
                 v                    v
      =================================================
      ||               THE SHARED HEAP               ||
      ||                                             ||
      ||   [ BankAccount Object (Shared Resource) ]  ||
      ||   > balance = $100                          ||
      ||                                             ||
      =================================================
```

## 2. Critical Section (The Danger Zone)

**The Concept:**
The **Critical Section** is the exact block of code where the shared resource is modified. 
Why is it dangerous? Because modifying a variable in Java is actually **three separate microscopic steps** for the computer: 
1. **READ** the value.
2. **MODIFY** the value.
3. **WRITE** the value back.

If a thread gets interrupted in the middle of these three steps, data gets corrupted. This corruption is called a **Race Condition**.

### 📊 VISUAL: The Race Condition Crash (No Locks)
Imagine `balance = 100`. Both threads want to withdraw $50.

```text
[TIME] | THREAD 1 (Withdraw $50)     | THREAD 2 (Withdraw $50)      | HEAP BALANCE
-------|-----------------------------|------------------------------|-------------
 T1    | READ balance (Sees $100)    |                              | $100
 T2    |                             | READ balance (Sees $100)     | $100
 T3    | MODIFY (100 - 50 = 50)      |                              | $100
 T4    |                             | MODIFY (100 - 50 = 50)       | $100
 T5    | WRITE (Saves 50 to Heap)    |                              | $50
 T6    |                             | WRITE (Saves 50 to Heap)     | $50 🚨 BUG!

🚨 OUTCOME: Both withdrew $50 (Total $100 taken), but the bank thinks only $50 was taken!
```

---

## 3. Mutual Exclusion (The Golden Rule)

**The Concept:**
**Mut**ual **Ex**clusion (Mutex) is the theoretical rule to fix the Race Condition. 
*   **Definition:** "If I am inside the Critical Section, you are excluded. You must wait until I am done."
*   **Analogy:** A fitting room in a clothing store. It only fits one person. If someone is inside, you wait outside.

## 4. Locking / Mutex in Java (THE DEEP DIVE)

This is where we get to the core of Java. How do we actually enforce Mutual Exclusion? We use **Locks**. Java gives us two main ways to lock our code: **Intrinsic Locks** and **Explicit Locks**.

### 📊 VISUAL: How a Mutex Lock Works
```text
           [ CRITICAL SECTION (The Fitting Room) ]
                     🔒 LOCK STATUS: UNLOCKED

1️⃣ Thread A arrives 🏃‍♂️ 
   -> Checks Lock -> It's Unlocked! 
   -> Grabs Key 🔑 -> Changes Status to 🔒 LOCKED.
   -> Enters Critical Section.

2️⃣ Thread B arrives 🏃‍♂️ 
   -> Checks Lock -> It's 🔒 LOCKED!
   -> 🛑 Thread B is BLOCKED. Goes to sleep in the "Waiting Pool". 💤

3️⃣ Thread A finishes 🚶‍♂️ 
   -> Returns Key 🔑 -> Changes Status to 🔓 UNLOCKED.
   -> Wakes up Thread B! 🔔

4️⃣ Thread B wakes up 🏃‍♂️ -> Grabs Key 🔑 -> Enters.
```

### Type A: Intrinsic Locks (`synchronized`)
Every single object in Java is born with a hidden, invisible lock inside it (called a Monitor). We use the `synchronized` keyword to activate it.

```java
class BankAccount {
    private int balance = 100;

    public void withdraw(int amount) {
        // We lock the specific Critical Section, using the current object's 'this' lock.
        synchronized(this) { 
            // 🔒 LOCK ACQUIRED BY THREAD
            if (balance >= amount) {
                balance -= amount; 
            }
            // 🔓 LOCK AUTOMATICALLY RELEASED HERE
        }
    }
}
```

### Type B: Explicit Locks (`ReentrantLock`) - *Enterprise Level*
The `synchronized` keyword is easy, but it has flaws. What if Thread B waits for the lock, but Thread A freezes forever? Thread B will wait forever (Deadlock)!

In professional Java, we use **Explicit Locks** from `java.util.concurrent.locks`. It gives us total control.

**Why is it called `Reentrant`?**
If Thread A owns the lock, and calls another method that *also* requires the same lock, it is allowed to "re-enter" without blocking itself. The lock just keeps a count (e.g., "Thread A holds this lock 2 times").

#### 🛠️ Code Example: ReentrantLock
```java
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class SafeBank {
    private int balance = 100;
    // 1. Create a physical Lock object
    private final Lock myMutex = new ReentrantLock();

    public void withdraw(int amount, String threadName) {
        
        // 2. Try to acquire the lock. 
        // We use tryLock() to say: "Try to get the lock, but don't wait forever!"
        if (myMutex.tryLock()) { 
            try {
                System.out.println("✅ " + threadName + " GOT THE LOCK!");
                
                // --- CRITICAL SECTION ---
                if (balance >= amount) {
                    balance -= amount;
                    System.out.println(threadName + " withdrew. Balance: " + balance);
                }
                // ------------------------

            } finally {
                // 3. ALWAYS release the lock in a finally block!
                // If the code crashes inside the try block, the lock STILL gets released.
                myMutex.unlock(); 
                System.out.println("🔓 " + threadName + " RELEASED THE LOCK!");
            }
        } else {
            // 4. If the lock was taken by someone else, we do NOT wait! We do something else.
            System.out.println("❌ " + threadName + " couldn't get the lock. Trying again later!");
        }
    }
}
```

## 5. Semaphore (The Traffic Controller)

**The Concept:**
A Mutex Lock allows exactly **ONE** thread in. 
A Semaphore allows exactly **N** threads in. 

*   **Analogy:** A parking lot with exactly 3 empty spaces. The gate allows 3 cars in. When the 4th car arrives, the gate stays shut until a car leaves.
*   **Permits:** A Semaphore uses a counter called "Permits". (E.g., 3 spaces = 3 permits).

### 📊 VISUAL: Semaphore Logic (3 Permits)
```text
[ SEMAPHORE GATE ] ---> [ AVAILABLE PERMITS: 3 ]

🚗 Thread 1 calls acquire() -> Permits become 2 -> Thread 1 ENTERS.
🚗 Thread 2 calls acquire() -> Permits become 1 -> Thread 2 ENTERS.
🚗 Thread 3 calls acquire() -> Permits become 0 -> Thread 3 ENTERS.
🚗 Thread 4 calls acquire() -> Permits = 0! 🛑 THREAD 4 WAITS AT GATE.

(Later...)
🚗 Thread 1 calls release() -> Permits become 1 -> GATE OPENS! 
🚗 Thread 4 wakes up, grabs the permit (Permits become 0) -> Thread 4 ENTERS.
```

### 🛠️ Code Example: Semaphore
This is highly used in real-world servers to limit how many users can download a file at the exact same time (to prevent server crashes).

```java
import java.util.concurrent.Semaphore;

class FileServer {
    // We only allow 2 threads to download at the same time
    private Semaphore downloadLimit = new Semaphore(2);

    public void downloadFile(String user) {
        try {
            System.out.println(user + " is requesting to download...");
            
            // 1. Grab a permit. If 0 permits exist, thread pauses here.
            downloadLimit.acquire(); 
            
            System.out.println("⬇️ " + user + " is DOWNLOADING... (Permits left: " + downloadLimit.availablePermits() + ")");
            Thread.sleep(2000); // Simulate the time it takes to download
            
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            // 2. Return the permit back to the Semaphore
            System.out.println("✅ " + user + " FINISHED. Releasing permit.");
            downloadLimit.release(); 
        }
    }
}
```
