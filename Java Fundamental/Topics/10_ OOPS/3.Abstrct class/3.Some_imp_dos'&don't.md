## 2. The DO's ✅ (Best Practices)

### ✅ DO: Always use the `@Override` annotation
When your child class provides the body for an abstract method, always put `@Override` right above it. 

**Why?** It tells Java to double-check your work. If you accidentally misspell the method name, Java will give you a helpful error immediately instead of creating a hidden bug.

```java
public abstract class Worker {
    public abstract void doWork();
}

public class Programmer extends Worker {
    
    // ✅ DO THIS: It makes your code safer!
    @Override
    public void doWork() {
        System.out.println("Writing Java code...");
    }
}
```

### ✅ DO: Use Abstract Classes to share common code
If you have three child classes that all need the exact same method, don't write it three times! Write it once as a *regular* method inside the abstract parent class.

**Why?** This prevents code duplication (repeating yourself).

```java
public abstract class GameCharacter {
    // ✅ DO THIS: Shared code written only once!
    public void jump() {
        System.out.println("Jumping into the air!");
    }
    
    public abstract void attack(); // Unique for each character
}
```

## 3. The DON'Ts ❌ (Common Mistakes to Avoid)

### ❌ DON'T: Try to create an object of an abstract class
Remember, an abstract class is just an idea or a blueprint. You cannot bring it to life directly.

**Why?** Because it has missing pieces (abstract methods with no bodies).

```java
public abstract class Shape {
    public abstract void draw();
}

public class Main {
    public static void main(String[] args) {
        
        // ❌ DON'T DO THIS: This will cause a compiler error!
        // Shape myShape = new Shape(); 
        
        // ✅ INSTEAD, create objects of the concrete child classes
        // Circle myCircle = new Circle();
    }
}
```

### ❌ DON'T: Make abstract methods `private`
An abstract method is a rule that a child class *must* follow. If you make it `private`, the child class cannot see it! 

**Why?** `private` means "only visible inside this exact class." Abstract methods must be visible to child classes so they can be overridden. Use `public` or `protected` instead.

```java
public abstract class Account {
    
    // ❌ DON'T DO THIS: Child classes can't see private methods!
    // private abstract void calculateInterest(); 
    
    // ✅ DO THIS: Child classes can see and override this.
    protected abstract void calculateInterest(); 
}
```

### ❌ DON'T: Make abstract methods `final`
In Java, the word `final` means "this cannot be changed or overridden." But the whole point of an abstract method is that the child class *must* override it! 

**Why?** `abstract` and `final` are exact opposites. Java will not let you use them together.

```java
public abstract class Device {
    
    // ❌ DON'T DO THIS: It contradicts itself!
    // public final abstract void turnOn();
    
    // ✅ DO THIS: Keep it abstract so the child can override it.
    public abstract void turnOn();
}
```

## 4. Summary Concept: "Is-A" Relationship

As a final tip, only use an abstract class when you can honestly say the child **"is a"** type of the parent.

* A `Car` **is a** `Vehicle`. (Good use of abstract class)
* A `Dog` **is an** `Animal`. (Good use of abstract class)
* A `Car` **is not a** `Engine`. (Bad use! A car *has an* engine. This is a different concept called composition).

Keep practicing these rules, and your Java code will look incredibly professional!
