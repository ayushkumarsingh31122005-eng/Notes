## 1. The Strict Contract: What Happens If You Break It?

We said an Interface is a "Contract." But who enforces this contract? **The Java Compiler.** 

When you type `implements`, you are making a legal promise to Java. If you break it, your code will completely refuse to run.

### Example: Breaking the Contract
```java
public interface PaymentMethod {
    void pay(int amount);
    void refund(int amount);
}

// ❌ ERROR! The compiler will show a red line under 'CreditCard'
public class CreditCard implements PaymentMethod {
    
    // We implemented pay...
    public void pay(int amount) {
        System.out.println("Paid $" + amount);
    }
    
    // BUT WE FORGOT TO IMPLEMENT refund()!
}
```

**The Fix:** You *must* provide the `refund()` method, OR you must declare the `CreditCard` class as `abstract` (which means it's unfinished).

## 2. The Modern "Diamond Problem" (Java 8 Conflict)

Earlier, we learned that Interfaces solve the **Diamond Problem** because interfaces didn't have method bodies. 
But wait... in Java 8, we introduced `default` methods (which *do* have bodies). So, what happens if you implement two interfaces that have the exact same default method?

```text
       [Interface A]              [Interface B]
    default void greet()       default void greet()
    { print("Hello A"); }      { print("Hello B"); }
                  \                  /
                   \                /
                 [Class MyClass] 🚨 CONFLICT!
```

Java gets confused again! *"Which greet() do I use?"*
To fix this, Java forces **YOU** to resolve the conflict by overriding the method in your class.

### How to resolve the conflict:
```java
interface Camera {
    default void turnOn() {
        System.out.println("Camera is ON");
    }
}

interface Radio {
    default void turnOn() {
        System.out.println("Radio is ON");
    }
}

// SmartPhone implements both!
public class SmartPhone implements Camera, Radio {
    
    // YOU MUST OVERRIDE the conflicting method
    @Override
    public void turnOn() {
        // You can write your own code:
        System.out.println("Smartphone booting up...");
        
        // OR you can specifically choose one of the parents' methods like this:
        Camera.super.turnOn(); 
    }
}
```

## 3. The Ultimate Architecture: Using Interfaces & Abstract Classes Together

In top MNCs (Multinational Corporations), we rarely choose *between* an Interface and an Abstract Class. **We use them together.**

This is a very famous design pattern. 
1. The **Interface** defines *WHAT* the system can do.
2. The **Abstract Class** provides *SOME* basic setup (the things that are the same for everyone).
3. The **Normal Class** finishes the specific details.

### Visual Architecture:
```text
[ Interface: Playable ]  <--- The rule: Must be able to play and stop.
         |
      (implements)
         |
[ Abstract Class: AudioDevice ] <--- The setup: Has volume control, power state.
         |
      (extends)
         |
[ Class: MP3Player ]  <--- The final product: Specifically plays MP3 files.
```

### The Code:
```java
// 1. The Interface (The Rules)
interface Playable {
    void play();
    void stop();
}

// 2. The Abstract Class (The shared foundation)
// Note: It doesn't have to implement play() and stop() because it is abstract!
abstract class AudioDevice implements Playable {
    int volume = 50; // Normal variable! Interfaces can't have these.
    
    // A shared method that all audio devices will use
    public void volumeUp() {
        volume++;
        System.out.println("Volume is now: " + volume);
    }
}

// 3. The Concrete Class (The real object)
class MP3Player extends AudioDevice {
    // Now we MUST provide the rules from the Playable interface
    @Override
    public void play() {
        System.out.println("Playing MP3 music track...");
    }

    @Override
    public void stop() {
        System.out.println("Stopping MP3 track.");
    }
}
```
*This is how real-world Java applications (like Android apps or Enterprise web servers) are built!*

## 4. Lambda Expressions: The Magic of Functional Interfaces

Let's look deeper at the `->` arrow symbol from Java 8. 
Why was the **Functional Interface** (an interface with exactly one method) created? 

Before Java 8, if you wanted to pass a simple action (like "print this" or "calculate that") into a function, you had to write a massive, ugly block of code called an *Anonymous Inner Class*. 

Lambdas let you pass **Behavior** (a block of code) as a variable.

### Real-World Example: Using Java's built-in `Runnable` Interface

Java has a built-in interface called `Runnable` used for running background tasks.
```java
// This is what Java's built-in interface looks like behind the scenes:
@FunctionalInterface
public interface Runnable {
    void run();
}
```

Here is how we used to use it vs how we use it now:

```java
public class Main {
    public static void main(String[] args) {
        
        // ❌ THE OLD WAY (Pre-Java 8) - Very long and messy
        Runnable oldTask = new Runnable() {
            @Override
            public void run() {
                System.out.println("Running background task the old way!");
            }
        };
        
        // ✅ THE MODERN WAY (Lambda) - Clean and beautiful
        // We don't need to write 'new Runnable' or 'public void run()'. 
        // Java is smart enough to guess it because there is only ONE method in the interface!
        
        Runnable modernTask = () -> System.out.println("Running task with Lambda!");
        
        // Running them
        oldTask.run();
        modernTask.run();
    }
}
```
**How to read `() ->` :** 
Read it as: *"Take zero parameters `()`, and do this `->` action."*
